## Member registration path — added release requirement
- The current Android WebView login page in `app/src/main/assets/index.html` contains the existing member login, Developer login and guest recommendation login paths; a public member self-registration form was not found in the inspected page.
- Do not fake registration by accepting arbitrary credentials or creating a local Godot-only account.
- Registration entry should be clearly accessible from the member login panel (e.g. “Belum terdaftar? Daftar Member Baru”), with a form collecting only approved fields such as display name, unique username, password and password confirmation.
- Registration must be implemented against a trusted server action and database schema. New registrations must be assigned a non-privileged status/role and must not receive active member access or enter the 3D world until server-side approval/activation policy is satisfied.
- Validate username uniqueness, input bounds, password strength, duplicate/retry behavior, rate limiting, and account creation consistency across Supabase Auth and `fc_members`. Do not expose service-role credentials in client code.
- Release acceptance: existing member login remains unchanged; registration submission succeeds/fails with understandable feedback; pending/inactive registrations are denied world entry; staff approval/activation follows existing member-management rules; verified active members enter the Godot world.


## Registration implementation findings (repository review)
- The existing `fc-member-auth` Edge Function has explicit `login` and `activate` actions, but the inspected action list does not include a self-service `register` action.
- Migration `202611220002_member_auth_activation.sql` defines one-time activation codes keyed to an already-existing `fc_members` row. The consume function only links Auth identity to a row with `status='Aktif'`, no existing `auth_user_id`, and a valid unused activation code. This is not a public registration/onboarding flow for a new applicant.
- Therefore the Android registration UI should not call `activate` as if it were new-member registration. A separate server-controlled application flow is needed, with pending applicant records or equivalent moderation queue, uniqueness checks, abuse/rate controls, and an approved staff action that creates/links the member record and issues activation.
- The current registration UI should expose a request/application flow only; must not allow applicant self-select roles or statuses, and should not create active member credentials until approval/activation is complete.
- Release test cases: invalid/duplicate username, malformed inputs, repeat submission/idempotency, server rejection/network failure, pending application, staff approval, activation redemption, normal login, and rejection of pending/inactive accounts at world-session verification.
